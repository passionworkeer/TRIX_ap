# Agent 集群质量保证流程 v2.0

## 🎯 核心原则

**质量优先，安全第一，小步快跑**

每个改动都必须：
1. ✅ 通过安全专家审查
2. ✅ 通过质疑 Agent 挑战
3. ✅ 小改动 + Git 提交
4. ✅ 完整测试覆盖

---

## 🤖 新增专家：质疑 Agent

### 角色定位
**"唱反调"** 的质量把关者，负责挑刺和找问题

### 核心职责
1. **质疑设计** - "这个设计是否过度复杂？"
2. **挑刺漏洞** - "这里是否有安全漏洞？"
3. **性能质疑** - "这会不会造成性能问题？"
4. **可维护性** - "这个代码未来难以维护"
5. **成本质疑** - "这个方案成本太高"

### 质疑清单
```markdown
## 质疑 Agent 必问的问题

### 1. 设计质疑
- ❓ 是否有更简单的方案？
- ❓ 是否过度设计？
- ❓ 是否违反 KISS 原则？

### 2. 安全质疑
- ❓ 是否有 SQL 注入风险？
- ❓ 是否有 XSS 风险？
- ❓ 认证授权是否完善？
- ❓ 是否泄露敏感信息？

### 3. 性能质疑
- ❓ 数据库查询是否最优？
- ❓ 是否有不必要的重渲染？
- ❓ 是否会导致内存泄漏？

### 4. 可维护性
- ❓ 代码是否容易理解？
- ❓ 是否有足够的注释？
- ❓ 是否容易测试？

### 5. 成本质疑
- ❓ 开发成本是否合理？
- ❓ 维护成本是否可控？
- ❓ 是否有更便宜的方案？
```

## 🔄 新的工作流程

### 完整流程图

```
用户需求
    ↓
【阶段 1: 需求分析】
主 Agent + 质疑 Agent
    ├─ 主 Agent: 分析需求
    ├─ 质疑 Agent: 挑战需求
    └─ 输出: 精炼的需求文档
    ↓
【阶段 2: 方案设计】
主 Agent + 相关专家 + 质疑 Agent
    ├─ 专家: 设计方案
    ├─ 质疑 Agent: 质疑设计
    ├─ 安全专家: 审查安全
    └─ 输出: 经过挑战的方案
    ↓
【阶段 3: 小步实施】
单专家 + 质疑 Agent + 安全专家
    ├─ 专家: 实现小功能
    ├─ 质疑 Agent: 挑刺实现
    ├─ 安全专家: 安全审查
    └─ 迭代直到通过
    ↓
【阶段 4: 代码审查】
安全专家 + 质疑 Agent
    ├─ 安全专家: 全面安全审查
    ├─ 质疑 Agent: 挑刺代码质量
    └─ 输出: 审查报告
    ↓
【阶段 5: 测试验证】
测试专家 + 质疑 Agent
    ├─ 测试专家: 编写测试
    ├─ 质疑 Agent: 质疑测试覆盖
    └─ 迭代直到 80%+ 覆盖率
    ↓
【阶段 6: Git 提交】
主 Agent + 安全专家
    ├─ 主 Agent: Git commit
    ├─ 安全专家: 最终检查
    └─ 输出: 完整的提交记录
    ↓
交付给用户
```

## 📝 实际示例

### 示例 1: 添加登录功能

#### 传统流程 (❌ 不安全)
```
1. 前端专家实现登录界面
2. 后端专家实现登录 API
3. 数据库专家创建 users 表
4. 完成 ❌ (有安全漏洞！)
```

#### 新流程 (✅ 安全)
```
1. 【需求分析】
   - 主 Agent: 分析登录需求
   - 质疑 Agent: "是否必须自己实现？可以用 Supabase Auth 吗？"
   - 优化: 使用 Supabase Auth

2. 【方案设计】
   - 主 Agent: 设计登录流程
   - 质疑 Agent: "是否需要记住登录状态？如何处理 token 过期？"
   - 安全专家: "必须使用 HTTPS，密码必须哈希"
   - 优化: 完整的安全方案

3. 【小步实施 1/3】
   - 前端专家: 实现登录表单
   - 质疑 Agent: "表单验证是否足够？是否有限速？"
   - 安全专家: "是否有 CSRF 防护？"
   - 迭代: 添加验证和限流

4. 【小步实施 2/3】
   - 前端专家: 集成 Supabase Auth
   - 质疑 Agent: "错误处理是否完善？"
   - 安全专家: "token 存储是否安全？"
   - 迭代: 使用 httpOnly cookie

5. 【小步实施 3/3】
   - 前端专家: 实现路由保护
   - 质疑 Agent: "未登录用户是否能直接访问？"
   - 安全专家: "检查通过 ✅"

6. 【代码审查】
   - 安全专家: 全面安全审查 ✅
   - 质疑 Agent: 代码质量挑刺 ✅
   - 测试专家: 测试覆盖率 87% ✅

7. 【Git 提交】
   - 主 Agent: 提交代码
   - 安全专家: 最终检查 ✅
   - 质疑 Agent: 最终确认 ✅

8. 【交付】
   ✅ 安全、高质量、可维护的登录功能
```

## 🔧 质疑 Agent 工作模式

### 质疑维度

#### 1. 设计维度
```
❓ 这个设计是否过于复杂？
❓ 是否违反 SOLID 原则？
❓ 是否有更简单的方案？
❓ 未来扩展性如何？
```

#### 2. 安全维度
```
❓ 是否有 SQL 注入风险？
❓ 是否有 XSS 风险？
❓ 认证授权是否完善？
❓ 是否泄露敏感信息？
❓ 是否有 CSRF 风险？
```

#### 3. 性能维度
```
❓ 是否有 N+1 查询？
❓ 是否有不必要的重渲染？
❓ 是否会导致内存泄漏？
❓ 数据库索引是否合理？
```

#### 4. 可维护性
```
❓ 代码是否容易理解？
❓ 是否有足够的注释？
❓ 是否容易测试？
❓ 命名是否清晰？
```

#### 5. 成本维度
```
❓ 开发成本是否合理？
❓ 维护成本是否可控？
❓ 是否有更便宜的方案？
❓ ROI 是否合理？
```

### 质疑输出格式

```markdown
## 💥 质疑 Agent 审查报告

### 🎯 任务: 实现用户登录功能

### ⚠️ 严重问题 (必须修复)

1. **安全漏洞: 未验证输入**
   - 位置: `src/components/Login.tsx:45`
   - 问题: 邮箱格式未验证
   - 修复: 添加 email 格式验证

2. **设计问题: 过度设计**
   - 位置: `src/services/authService.ts:120`
   - 问题: 实现了自定义 token 管理，可以直接用 Supabase
   - 建议: 删除自定义实现，使用 Supabase Auth

### ⚡ 性能问题

1. **不必要的重渲染**
   - 位置: `src/components/Login.tsx:78`
   - 问题: 每次 state 变化都重渲染整个表单
   - 优化: 使用 React.memo

### 📚 可维护性问题

1. **缺少注释**
   - 位置: `src/utils/passwordValidator.ts:15`
   - 问题: 复杂的正则表达式无注释
   - 建议: 添加注释解释规则

### 💰 成本质疑

1. **开发成本过高**
   - 问题: 自实现了完整的认证系统
   - 建议: 使用 Supabase Auth，节省 80% 开发时间

### ✅ 通过项

- 密码哈希算法正确 (bcrypt, cost=12)
- 使用了 HTTPS (生产环境)
- 有基本的错误处理

### 📊 总体评分

- 安全性: 6/10 (有严重问题)
- 性能: 7/10 (有优化空间)
- 可维护性: 6/10 (缺少文档)
- 成本效益: 5/10 (过度设计)

### 🎯 结论

**不通过** ⛔

必须修复所有严重问题后才能继续。
```

## 🚀 小步快跑策略

### 每次改动的上限

```
✅ 单次改动: 50-100 行代码
✅ 单次改动: 1-2 个文件
✅ 单次改动: 1 个功能点
✅ 单次改动: 1 个专家主导

❌ 避免大重构
❌ 避免同时改多个文件
❌ 避免同时改多个功能
```

### Git 提交频率

```
✅ 每个小改动后立即提交
✅ 提交信息清晰明了
✅ 提交前通过所有质量门禁

示例:
feat: 添加登录表单基础结构
feat: 实现邮箱验证逻辑
feat: 集成 Supabase Auth
fix: 修复登录后未跳转问题
test: 添加登录流程测试
```
