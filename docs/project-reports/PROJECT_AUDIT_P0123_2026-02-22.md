## 四、待修复问题（P0/P1/P2 分级）

### P0 - 必须立即修复（安全/致命缺陷）

#### P0-1: Socket 身份未做服务端鉴权
- **问题描述**: `clawbot-channel` 直接信任客户端上报的 `userId` 和 `deviceId`
- **影响**: 可冒充任意用户查询配对状态、接收/发送 Bot 消息
- **证据**: `server/clawbot-channel/server.js:360` (`app_register` 直接使用 `data.userId`)
- **修复建议**:
  1. Socket 握手强制携带 Supabase JWT
  2. `socket.userId` 从已验证 Token 提取
  3. Bot 侧增加设备级密钥或签名挑战

#### P0-2: Webhook 鉴权空配置放行
- **问题描述**: `CLAWBOT_WEBHOOK_SECRET` 未配置时 webhook 误放行
- **影响**: 外部可伪造 Bot 回调注入消息
- **证据**: `server/clawbot-channel/server.js:120-121`
- **修复建议**:
  1. 启动时强制校验 `CLAWBOT_WEBHOOK_SECRET` 非空
  2. 鉴权逻辑增加显式空值检查

#### P0-3: 敏感配置已提交到仓库
- **问题描述**: `.env`、`server/clawbot-channel/.env` 包含 webhook secret 与 OSS AK/SK
- **影响**: 密钥泄露可导致 webhook 伪造、OSS 资源滥用
- **证据**: `server/clawbot-channel/.env:18,26,27`
- **修复建议**:
  1. 立即轮换已暴露密钥
  2. 从 Git 历史彻底清理敏感文件
  3. 更新 `.gitignore`

#### P0-4: SQLite 数据文件在版本控制中
- **问题描述**: 运行时数据库文件被跟踪
- **影响**: 用户/设备数据泄露、环境间数据串扰
- **证据**: `server/clawbot-channel/data/pairing.db*`
- **修复建议**:
  1. 将 DB 路径迁移到仓库外
  2. 从版本控制移除

### P1 - 核心功能风险（影响用户体验）

#### P1-1: 配对状态脏写
- **问题描述**: `pair_with_token` 先绑定用户再检查 Bot 在线
- **影响**: Bot 离线时仍可能写入用户绑定
- **修复建议**: 先检查 Bot 在线，再执行绑定

#### P1-2: 消息确认链路不完整
- **问题描述**: `app_message` 异常分支使用作用域外 `messageId`
- **影响**: 出错时确认事件可能发送失败
- **修复建议**: 将 `messageId` 提升到 `try` 外层作用域

#### P1-3: sendMessage API 契约不一致
- **问题描述**: Context 暴露 `sendMessage: (...) => void`，但调用方用 `await`
- **影响**: 发送失败不会进入 `catch`，乐观 UI 回滚不可靠
- **修复建议**: 改为返回 `Promise<void>` 并向上传播失败

#### P1-4: OSS 接口缺少鉴权
- **问题描述**: `/oss/signed-url`、`/upload`、`/upload/base64` 无鉴权
- **影响**: 任意外部请求可上传文件、消耗 OSS 成本
- **修复建议**:
  1. 为这三类接口加 JWT 鉴权
  2. 签名 URL 限制 key 前缀

#### P1-5: 数据库脚本与运行时代码漂移
- **问题描述**: `database/INIT_ALL.sql` 与前端代码 schema 不一致
- **影响**: 用错初始化脚本时功能异常
- **修复建议**:
  1. 仅保留一个权威初始化入口
  2. 迁移为版本化 migration

#### P1-6: 部署脚本仍指向 nanobot
- **问题描述**: `deploy.sh` 部分命令仍引用已弃用的 nanobot
- **影响**: 运维可能重启错误服务
- **修复建议**: 移除 nanobot 相关部署逻辑

### P2 - 重要但可并行排期

#### P2-1: WebSocket 配对接口无限流
- **问题描述**: `pairingLimiter` 已定义但未生效
- **影响**: 配对码/Token 接口可被高频尝试
- **修复建议**: 在配对事件层加基于 IP+socket 的限流

#### P2-2: QR 配对密钥管理弱
- **问题描述**: 内置默认 Token + localStorage 持久化
- **影响**: Token 泄露后可复用
- **修复建议**:
  1. 移除硬编码默认 Token
  2. 改为一次性短时令牌

#### P2-3: 环境模板含硬编码地址
- **问题描述**: `.env.example` 和 `.env.production` 含真实地址
- **影响**: 跨环境易误配
- **修复建议**:
  1. `.env.example` 仅保留占位符
  2. 生产环境变量由 CI/CD 注入

#### P2-4: 后端依赖存在高危审计项
- **问题描述**: `npm audit` 报告 `9 high`，集中在 `sqlite3` 依赖链
- **影响**: 安装/构建阶段安全风险
- **修复建议**:
  1. 升级 `sqlite3` 及依赖链
  2. 将 `npm audit` 加入 CI 阻断阈值

#### P2-5: 缺少自动化测试
- **问题描述**: 前后端均缺少自动化测试脚本
- **影响**: 回归风险完全依赖人工验证
- **修复建议**:
  1. 补充配对链路和消息 ACK 集成测试
  2. 前端补关键页面 smoke 测试
